# F#/.NET Architecture Analysis Specifics

## 1. Solution, Projects, and File Order
* Analyze `.sln`/`.slnx`: identify projects, their `<ProjectReference>` graph, and which are libraries vs entry points.
* **Central package management:** distinguish `Directory.Packages.props` (central versions) from per-project `PackageReference` versions, `Directory.Build.props`/`Directory.Build.targets` (shared settings), and `global.json` (SDK pin). Central files are the single source of truth; record per-project deviations as architectural decisions.
* **Compile order:** F# compiles files in explicit `<Compile Include>` order — earlier files cannot reference later ones. The order is a compiler-enforced dependency DAG; read it as the layering map. Cyclic dependencies cannot hide behind namespaces.
* Separate public API from internal implementation via `.fsi` signature files (the F# equivalent of `pub` boundaries), `internal`/`private` modifiers, and `[<InternalsVisibleTo>]` allowances.
* Define layer boundaries: Domain Logic, I/O Infrastructure, Interop/UI.

## 2. Conditional Compilation and Codegen
* **`#if` directives:** map `#if DEBUG`/`#if TRACE`/custom `DefineConstants` branches and `TargetFrameworks`/`RuntimeIdentifiers` conditions in `.fsproj`. Different TFMs or publish modes can form different architectures.
* **Type Providers:** identify type-provider usage (`FSharp.Data`, Swagger/OpenAPI providers, `SQLProvider`). They generate types at compile time from external schemas — the schema source is part of the API contract and an external coupling point.
* **Build-time codegen:** find code generated by MSBuild targets — resx, protobuf/gRPC, `LibraryImport` source generation. Record generated-vs-handwritten boundaries.
* **Publish modes:** check `PublishAot`/`PublishTrimmed`/`PublishSingleFile`/`PublishReadyToRun` — these constrain reflection, dynamic loading, and interop assumptions.

## 3. Types, Abstractions, and Domain Modeling
* **Discriminated unions:** identify domain states modeled as DUs (Type-State and State Machine patterns) vs boolean/`option` soup where invalid states remain representable.
* **Nominal types:** single-case DU wrappers and `[<Measure>]` units of measure for domain primitives — check where primitive obsession admits silent argument swaps.
* **Value vs reference semantics:** record `[<Struct>]` records/DUs, `voption` vs `option`, `byref`/`inref`/`outref`, `Span<'T>`/`Memory<'T>` — these define allocation and memory layout in hot paths.
* **Abstractions:** interfaces and object expressions define extension points; SRTP (`inline` + member constraints) is compile-time static dispatch erased at runtime.
* **Serialization boundaries:** `JsonPropertyName`/`JsonConstructor`/`DataContract` attributes, `FSharp.SystemTextJson`, Thoth, Newtonsoft — attributes mark types crossing process/persistence boundaries. Separate serializable DTOs from internal domain types.

## 4. State, Agents, and Message Passing
* **Shared state:** trace `ref`/`mutable` fields, `Dictionary`/`ConcurrentDictionary`/`ResizeArray`/`HashSet`, `Lazy`, `ThreadLocal`/`AsyncLocal`, and their guards (`lock`, `Monitor`, `Interlocked`, `ReaderWriterLockSlim`, `SemaphoreSlim`).
* **Agents & channels:**
  * Map `MailboxProcessor` agents (the actor pattern) and `System.Threading.Channels`/`BlockingCollection` pipelines.
  * Record `PostAndReply`/`PostAndAsyncReply` request-reply pairs and identify agent loops that own mutable state.
  * **Backpressure:** `MailboxProcessor` queues are unbounded — check for bounded `Channel` alternatives and behavior under saturation (blocking, dropping, `TryPost` failure).
* **Confinement:** identify where mutable state is confined to a single agent or thread — these are the intended invariants the architecture relies on.

## 5. Async, Tasks, and Cancellation
* **CE varieties:** distinguish `task` (hot, resumable code, `SynchronizationContext` capture) from `async` (cold, implicit cancellation checks at bind points, thread-pool hops). Record which is used where and why.
* **Conversion edges:** map `Async.AwaitTask`/`Async.StartAsTask`/`Async.StartImmediate`/`Async.StartChild`/`TaskCompletionSource`/`ValueTask` — check whether `CancellationToken` and exceptions survive each boundary.
* **Background work:** find `Task.Run`, `Async.Start`, `Async.StartWithContinuations`, `Task.Factory.StartNew(LongRunning)` — long-running tasks and their supervision strategy (where exceptions surface).
* **Fire-and-forget:** unsupervised `Async.Start` or discarded tasks whose exceptions are unobserved.
* **`SynchronizationContext`:** UI/event-loop thread capture (`Async.StartImmediate`, `task` on a UI thread) is an architectural constraint — library code must not silently depend on the caller's context.
* **Sync-over-async:** `task.Result`, `.Wait()`, `Async.RunSynchronously`, `PostAndReply` — deadlock risks against context-owning threads.

## 6. Data Layer, Transactions, and Storage
* **Connection pooling:** identify `DbConnection`/`DbContext` pooling and lifetimes (`IDbContextFactory`, scoped DI lifetimes).
* **Transaction management:** document strategies — `IDbTransaction` explicit passing, `TransactionScope` ambient transactions (async-flow caveats), Unit of Work, repository interfaces.
* **Data access style:** map Dapper/micro-ORM, EF Core entity mapping boundaries, raw SQL, and SQL type providers — each defines a different domain-to-storage boundary.
* **Embedded & cache storage:** map SQLite/LiteDB/embedded KV usage, `IMemoryCache`/`IDistributedCache`, locking schemes, and snapshot/versioning behavior of persisted schemas.

## 7. Errors, Computation Expressions, and Unsafe
* **Errors & boundaries:**
  * Distinguish expected failures modeled as `Result<'T,'E>` with DU error types from exceptional `exn`/`raise`. Record where the line is drawn.
  * Check error isolation: infrastructure exceptions must not leak uncontrolled through public APIs (`try/with` translation, `Async.Catch`, `Result.catch`-style helpers). Flag `Result<'T, string>` and exceptions-as-control-flow across module boundaries.
* **Computation expressions:** catalog custom CEs (`result`, `async`, `task`, DSL builders) — they hide control flow and error semantics the way macros do in Rust.
* **Unsafe & `byref`:** find `fixed`/`NativePtr`/`voidptr`/`nativeint`, `byref`/`inref`/`outref`, `Span`/`Memory` slicing. Document pinning scopes, pointer lifetimes, and purpose — the `unsafe` analog of Rust's `// SAFETY:` invariants.

## 8. Observability and Telemetry
* **Logging:** document `ILogger` categories, `LoggerMessage`/`LoggerMessageAttribute` source-generated logging, and structured/event logging (`EventSource`).
* **Tracing & metrics:** map `ActivitySource`/`Activity` (OpenTelemetry-compatible distributed tracing), `System.Diagnostics.Metrics` (`Meter`, `Counter`, `Histogram`), and `EventCounter` — context propagation across `let!`/`await` and agent boundaries.
* **Ambient context:** `AsyncLocal` context flow through `async`/`task` hops — verify ambient correlation survives thread switches and `Async.StartImmediate`.
* **Event streams:** `Event`/`IObservable`/Rx pipelines as notification boundaries.

## 9. FFI, Interop, and C# Surface
* **P/Invoke:** distinguish `[<DllImport>]`/`extern` declarations from source-generated `[<LibraryImport>]`, and `[<UnmanagedCallersOnly>]` reverse callbacks. Record `MarshalAs`, `StructLayout`, `SetLastError`, `CallingConvention` fidelity at each boundary.
* **Native lifetimes:** `SafeHandle` subclasses, `GCHandle` pinning, delegate rooting for native callbacks, `Marshal.AllocHGlobal`/`FreeHGlobal` pairing — release guarantees on exception paths.
* **C# consumer surface:** `FSharpAsync`/`FSharpOption`/`FSharpFunc` and DU encodings in APIs consumed from C# — `[<CompiledName>]`, `[<Extension>]`, `[<AbstractClass>]`, `[<CLIMutable>]`, `CLSCompliant` mark intended interop ergonomics.

## 10. Test Organization
* **Frameworks:** identify test projects and frameworks (xUnit, NUnit, Expecto, MSTest) — collection/parallelization attributes affect shared-state test correctness.
* **Property tests:** FsCheck properties as executable invariants — document which invariants are covered.
* **Structure:** reflect whether tests cover layers independently (unit) or across boundaries (integration). Highlight coverage gaps in key components.
* **Scripts:** `.fsx` scripts and `dotnet fsi` as REPL probes of the public API.

## 11. Analysis Tools
* `dotnet list package --outdated|--deprecated|--vulnerable|--include-transitive` — Dependency audit.
* `dotnet restore --locked-mode` / NuGet lock files (`packages.lock.json`) — Reproducibility and drift detection.
* `dotnet build --warnaserror` — The F# compiler is the primary linter.
* `dotnet fsharplint lint` — Structural/architectural rule checks (where configured).
* `dotnet fantomas --check` — Formatting consistency.
* `dotnet fsi` — Interactive type and module inspection.
* `dotnet-counters` / `dotnet-trace` / `dotnet-gcdump` / `dotnet-dump` — GC pressure, contention, thread state, and leak analysis.
* BenchmarkDotNet — Verify hot-path allocation and throughput claims.
* F# analyzers (`fsharp-analyzers` SDK) — Custom structural checks, e.g. unused-opens and cyclic dependency detection, where configured.
